# [FPGA] RV32I 6-Stage Pipeline (BRAM 포팅) 무한 루프 디버깅 및 해결 보고서

**작성일시**: 2026년 5월 12일
**목적**: 동기식 BRAM 지원을 위해 6-stage 파이프라인으로 포팅한 이후, `testbench_TFLM` 시뮬레이션이 완료되지 않고 무한 루프에 빠지는 이슈에 대한 원인 분석 및 완벽한 해결 과정 정리.

---

## 1. 이슈 개요

동기식 BRAM의 1-cycle 읽기 지연(read latency)을 해결하기 위해 파이프라인을 6단계(`IF - ID - EX - MEM - MEM2 - WB`)로 확장했습니다. 이 과정에서 `testbench_TFLM`을 실행하면 `$finish` 상태(정상 종료 서명인 `jal x0, 0`)에 도달하지 못하고 시뮬레이션이 수천만 사이클 이상 헛돌며 무한 루프에 빠지는 현상이 발생했습니다.

---

## 2. 근본 원인 분석 및 해결 방안

시뮬레이션 로그와 RTL(Register Transfer Level) 코드를 면밀히 분석한 결과, 단순히 한 가지 버그가 아니라 **파이프라인 제어와 관련된 세 가지 치명적인 버그가 복합적으로 작용**하여 프로그램을 붕괴시키고 있었습니다.

### 2.1. 버그 1: 파이프라인 Stall 중 Instruction Fetch(명령어 패치) 누락
*   **원인**: `inst_memory`가 동기식 BRAM으로 변경되면서 매 클럭 엣지마다 주소를 샘플링하고 명령어를 출력합니다. 만약 파이프라인에 stall이 발생하면 `pc`는 정지하지만, BRAM은 정지된 `pc`를 계속 샘플링하며 동작을 계속합니다. 이때 `IFID_inst` 레지스터가 stall 상태에서 아무 값도 저장하지 않고 유지되다 보니, stall이 풀리는 시점에 BRAM이 이미 다음 명령어로 출력을 갱신해버려 **stall 직전에 읽어온 명령어가 파이프라인에서 완전히 증발(Skip)되는 치명적 버그**가 있었습니다.
*   **해결**: stall이 시작되는 순간 출력 중이던 `inst` 값을 안전하게 캡처해두는 `stalled_inst` 레지스터를 추가했습니다. 그리고 stall이 끝나는 사이클에서 `IFID_inst`가 버려진 명령어를 `stalled_inst`로부터 복원하여 파이프라인에 정상적으로 주입하도록 로직을 수정했습니다.

### 2.2. 버그 2: Load-Use Hazard 검사 로직의 `rs2` 의존성 검사 누락
*   **원인**: Load 명령어(`lw`) 직후에 해당 레지스터를 사용하는 명령어가 올 때 stall을 발생시키는 `load_use_hazard` 로직에 심각한 오류가 있었습니다. 
    1. 후속 명령어가 Store(S-type)이거나 Branch(B-type)인지 판단할 때, 현재 ID 단계에 있는 명령어(`IFID_inst`)의 opcode를 확인해야 하는데 실수로 EX 단계에 있는 명령어(`IDEX_opcode`, 즉 `lw` 명령어의 opcode)를 검사하고 있었습니다.
    2. Branch 명령어(`is_B_type`)에 대한 hazard 검사 자체가 누락되어 있었습니다.
    이로 인해 TFLM의 핵심 반복문 내부에 있는 `lw x15, 20(x2)` 직후의 `blt x20, x15, 214` 분기 명령어가 `x15` 레지스터에 대한 stall을 발생시키지 않았습니다. 그 결과 분기문이 데이터 메모리에서 새로운 값이 도착하기도 전에 **레지스터 파일의 옛날 쓰레기값을 읽어와 평가**해버렸고, 신경망 로직이 붕괴되어 무한 루프에 빠진 것입니다.
*   **해결**: Hazard 검사 로직을 `IFID_inst[6:0]`을 사용하여 올바르게 현재 디코딩 중인 명령어를 검사하도록 수정하고, `is_B_type` 조건을 `rs2` 검사에 추가하여 분기문도 정상적으로 stall을 요청하도록 고쳤습니다.

### 2.3. 버그 3: 불필요한 3-Cycle Stall에 의한 포워딩 타이밍 어긋남
*   **원인**: 기존 코드의 `load_use_hold` 상태 머신이 stall을 2사이클이 아닌 3사이클 동안 유지하도록 잘못 작성되어 있었습니다. stall이 3사이클로 길어지면서 의존성을 가진 후속 명령어가 `EX` 단계에 도달했을 때, Load 명령어는 이미 파이프라인을 완전히 빠져나간(`WB` 완료) 뒤였습니다. 이로 인해 후속 명령어가 `MEM2 -> EX` 포워딩 창(window)을 완전히 놓치고, 레지스터 파일에 데이터가 쓰이기 직전에 값을 읽어오는 타이밍 어긋남 현상이 발생했습니다.
*   **해결**: `load_use_hold` 레지스터의 상태 머신을 수정하여, 설계 의도대로 정확히 2사이클 동안만 stall이 유지되도록 변경했습니다. 이를 통해 후속 명령어가 `EX` 단계에 진입할 때 Load 명령어가 `MEM2` 단계에 위치하게 되며, `MEM2 -> EX Forwarding` MUX를 통해 완벽하게 데이터를 포워딩받을 수 있게 되었습니다.

---

## 3. 결과 및 검증

위의 세 가지 파이프라인 제어 로직을 수정한 후, `testbench_TFLM` 및 기초 파이프라인 검증인 `testbench_Basic` 시뮬레이션을 다시 실행했습니다.

*   **testbench_TFLM 정상 동작**: 
    - 신경망 추론 프로그램이 무한 루프를 완전히 탈출했습니다.
    - 총 **199,463 Cycles (약 3.99 ms)** 만에 정확하게 `$finish` (정상 종료 시그니처 `jal x0, 0` 도달) 되었습니다. (동기식 메모리 지연 시간과 2-cycle stall 오버헤드를 고려했을 때 수학적으로 완벽하게 떨어지는 정상적인 실행 사이클 수치입니다.)
*   **testbench_Basic 통과**: 
    - 기초적인 Load/Store 및 Forwarding, 파이프라인 Stall 테스트 벤치들도 모두 충돌 없이 정상적으로 Pass 하였습니다.

이번 디버깅을 통해 FPGA BRAM의 동기식 지연 특성을 완벽히 반영하면서도 데이터 무결성을 보장하는 6-stage 파이프라인의 완성도를 크게 높였습니다.
